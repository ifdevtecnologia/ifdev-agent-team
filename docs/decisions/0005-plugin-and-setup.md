- **Labels:** **[V]** verified locally; **[D]** documented; **[R]** reported by the Codex review from the OpenAI docs, not checked by us; **[A]** assumption.

## Context

The owner asked whether installation could move from `scripts/install.sh` (links from a clone that must stay in place, no visible version) to plugins for Claude Code and Codex, without losing anything the toolkit delivers today. The owner is currently the only user, the clone is already updated with `git pull`, and the immediate need was knowing the installed version and state, which `scripts/status.sh` (#42) now provides. This record keeps the design so the analysis is not lost.

## Constraints

- A Claude Code plugin delivers `agents/` (named `<plugin>:<name>`; `tools` and `disallowedTools` apply, `permissionMode` and `hooks` do not), `skills/`, `hooks/hooks.json` and `bin/`, but **no** global `CLAUDE.md` and **no** rules [D] (0002). A SessionStart hook's `additionalContext` is capped at 10,000 characters per string [D]; the always-loaded instructions and rules are about 37 KB.
- Codex has plugins and marketplaces: `codex plugin marketplace add <owner/repo|path>` and `codex plugin add` [V]; bundled plugins in the cache use `.codex-plugin/plugin.json` with `skills: "./skills/"` and an `interface` block [V]; for new plugins a root `plugin.json` is the preferred format and `.codex-plugin/` a fallback [R]; repository marketplaces live in `.agents/plugins/marketplace.json` [D]. Plugins bundle skills, MCP servers, assets and hooks [D]; delivering `~/.codex/AGENTS.md` or custom agents (`~/.codex/agents/*.toml`) is not documented [D].
- Hook events differ: Claude's `StopFailure` and `Notification` have no Codex equivalent [R]. Codex plugin hooks stay inactive until the user trusts them [R], and plugins with lifecycle hooks are not eligible for the public OpenAI directory, which ChatGPT and Codex share [R].

## Options considered

| | A. Keep links + `status.sh` | B. Plugin only, lean instructions | **C. Plugin + setup** | D. Hybrid (0002) |
|---|---|---|---|---|
| Always-loaded instructions and rules | full | about 9 KB through the SessionStart hook; rules only as skills and inside agents | full, written by setup | full, linked |
| Codex roles with a clean context | yes (TOML copies) | lost (no `AGENTS.md`, no agents) | yes (role skills, see below) | yes |
| Version and update through a marketplace | no | yes | yes, plus rerunning setup | components only |
| Clone required | yes | no | no | yes |
| Effort | done | high, and it changes content | high | medium |

B loses the main agent's always-loaded rules and, on Codex, the global instructions and roles. D keeps the clone, so it does not remove the main reason for a plugin.

## Design (option C)

- **Plugin content.** Generated by `scripts/build_targets.py` into one root under `dist/` (or one per tool if a shared root proves ambiguous): Claude `agents/`, the eight skills, a `setup` skill with its script, a `payload/` with the same `CLAUDE.md`, rules and `AGENTS.md` as `dist/claude/` and `dist/codex/`, per-tool hooks (Claude: `Stop`, `StopFailure`, `Notification`; Codex: its own events) with copies of the notifier, and a short SessionStart hook that warns when setup never ran or wrote an older version. Manifest versions equal the CHANGELOG release. Marketplaces `.claude-plugin/marketplace.json` and `.agents/plugins/marketplace.json` at the repository root; names `ifdev` and `ifdev-agent-team` by default.
- **Setup.** A `setup` skill (never invoked implicitly) runs a script bundled inside the skill directory, because a plugin cannot reach files outside its root. It writes regular-file **copies**: for Claude, `~/.claude/CLAUDE.md` and the three rules; for Codex, `~/.codex/AGENTS.md`. It reuses the checksum ownership of the Codex agent copies (0004 amendment, issue #65), keeps dry run, idempotency, `--uninstall` and the refusal of symlinked parents, and extracts the copy helpers from `scripts/lib/common.sh` instead of duplicating them.
- **The user's own instructions.** Setup does not replace a `CLAUDE.md` or `AGENTS.md` that is not the toolkit's by default: it refuses and explains, and replaces only with `--replace` (after a backup) or guides a merge, because a backup keeps the bytes but not the behaviour. This differs from the installer's current choice (0004, owner decision 6). It warns when `~/.codex/AGENTS.override.md` exists.
- **State.** `~/.ifdev-ai-tools/` gains a schema version and the origin of every item (clone or plugin), so the installer, setup and uninstall never update or remove the other origin's items; migrating the current state is transactional.
- **Codex roles as skills.** Each role becomes a generated skill `role-<role>` from `core/agents/` (not invoked implicitly). The Codex adapter says: to run role X, spawn a subagent with `fork_turns: "none"` and tell it to load the skill `role-X` and follow it; never run a role in the main conversation. The subagent reads the skill itself, so the main agent does not paraphrase the role. This drops the eighteen TOML copies. Lost compared with TOML: the role is no longer a named agent type in `spawn_agent`, and the text arrives as a message instead of `developer_instructions`. The TOML files only carried `name`, `description` and `developer_instructions`, and Codex does not enforce read-only roles either way (0003).
- **Claude roles** stay plugin agents, named `ifdev:<role>` unless a bare name resolves (0002 assumption A2).
- **Coexistence.** Setup detects the installer's links to agents, skills and hooks and offers to remove only exact links to a toolkit checkout and the toolkit's hook entries, with a backup and a dry run, to avoid loading everything twice. The installer stays as the development path (links in place) until a later release retires it.
- **Official directories.** Submitting to the Anthropic marketplace and to the OpenAI directory are external publications that each need the owner's explicit authorization. The OpenAI directory needs a variant without hooks (skills, role skills and setup), which loses notifications and the version warning there [R]. Prerequisites: an icon and logo, privacy and terms pages if required, a stable release, and security and privacy reviews of what the plugin runs.

## What would and would not be lost

Kept: the full instructions and the three rules always loaded, the eighteen roles with their own context on both tools, the eight skills, the notification hooks and per-project overrides. New cost: rerunning setup after each plugin update (the hook warns, except in the public OpenAI variant). Lost only in the public OpenAI variant: notifications and the version warning.

## Proof of concept (first step if resumed)

In a temporary HOME (`env -i PATH HOME=$T CLAUDE_CONFIG_DIR=… CODEX_HOME=…`), without login or model calls except where noted:

1. Claude: local marketplace, `claude plugin install --json`, `plugin details` lists agents, skills and hooks; the setup script runs from the installed cache.
2. Claude: whether the Agent tool resolves a bare role name to `ifdev:<role>` (needs a model session) [A].
3. Codex: `codex plugin marketplace add <local dir>`, `codex plugin add`, `codex debug prompt-input` lists the plugin skills; which manifest location 0.167 reads.
4. Codex: plugin hooks load in the CLI (docs stress the desktop app) and stay inactive until trusted.
5. Codex: the setup skill resolves its own cached directory and can write to HOME under the default sandbox and approvals; whether `onboardingSkill` can offer setup on first use.
6. Codex: a subagent spawned with `fork_turns: "none"` sees the plugin's role skills and the global `AGENTS.md` and follows the loaded skill (needs a model session) [A]. If this fails, setup writes the eighteen TOML copies instead.
7. Whether one root with both manifests works without ambiguous precedence.

## Release gates (if implemented)

These must not be skipped because a CLI is missing; CI installs pinned CLIs or the release is PARTIAL: upgrade between two plugin versions, rollback after a failure midway through setup, a removed plugin with leftover payload, untrusted hooks, the public variant without hooks, a foreign `CLAUDE.md` or `AGENTS.md` and an `AGENTS.override.md`, and equivalence with today's inventory (thirty-three Claude items; eleven Codex links plus eighteen copies, which become eighteen role skills) counting plugin plus setup.

## Revisit when

- Another person or a team starts installing the toolkit, which brings back the need to install and update without a clone and to know each machine's version.
- Claude Code or Codex accept global instructions or rules from a plugin, or Claude Code raises the `additionalContext` cap; option B or a simpler C would then become viable.

Until then, `scripts/install.sh` remains the only supported installation and `scripts/status.sh` reports the version and state.
